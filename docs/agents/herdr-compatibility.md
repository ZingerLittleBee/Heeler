# herdr compatibility observations

Consult this reference for RPC framing, protocol negotiation, subscription
recovery, Agent launch/input, terminal attach, or remote scrolling behavior.
These observations were moved from `CLAUDE.md` without changing their evidence
versions. They are historical evidence, not fresh tests on the installed herdr.

## Current routing

- Unix API and Events use direct-streamlocal; Unix terminals use PTY exec
  ([ADR 0011](../adr/0011-libssh2-direct-streamlocal-transport.md)). Native
  Windows uses `remote-api-bridge` and `terminal session control`
  ([ADR 0018](../adr/0018-native-windows-hosts.md)); Unix forwarding refusal
  never selects the Windows path.
- herdr-core Hosts are a Server Kind of their own, never a fallback for a
  Herdr TUI Host. Each carries one framed connection to its core:
  direct-streamlocal on Unix, `herdr-core connect` over SSH exec on native
  Windows, and connecting never starts a core
  ([ADR 0031](../adr/0031-herdr-core-hosts-connect-without-starting-a-core.md)).
  Their Agents fill the Console's Herdr TUI-shaped models
  ([ADR 0032](../adr/0032-herdr-core-hosts-fill-the-console-models.md)).
- Initial API request timeout, herdr 0.9.5 (`INITIAL_REQUEST_TIMEOUT` in
  `src/api/server.rs`, source review): an accepted API socket closes after five
  seconds without a request line. In a #523 Simulator/Instabox test against
  herdr `2713feb56`, blocking SSH downlink for 18 seconds delayed the
  channel-open acknowledgement past that timeout. Recovery produced EOF before
  a response line, with `timed out reading api request` in the server log. This
  is a retryable channel failure, not evidence of an incompatible response;
  complete invalid JSON and oversized responses remain protocol errors. Recovery
  must not replay an operation that changes Host state.
- Start with [HeelerSSHTransport](../../Sources/Heeler/Transport/HeelerSSHTransport.swift)
  and [EventsSession](../../Sources/Heeler/Transport/EventsSession.swift) for
  current adapters and recovery. Older symbol names below belong to their
  observation's version; use the [source map](navigation.md) to reach current owners.
- The committed schema is [scripts/herdr-schema.json](../../scripts/herdr-schema.json).
  Generated types describe that snapshot, not every method in every herdr release.
- For native Windows setup or runtime acceptance, use the
  [setup guide](../guides/windows-setup.md) or
  [acceptance checklist](../guides/native-windows-testing.md).
- Chat ([ADR 0024](../adr/0024-native-chat-from-agent-transcripts.md)) reads
  transcripts over SFTP, and OpenCode's session store with a read-only exec
  ([ADR 0025](../adr/0025-opencode-chat-reads-its-session-store.md)), never
  through herdr. herdr supplies the session id, Agent Status, screen reads,
  `agent.prompt`, `agent.send_keys` and `pane.send_input`. For Codex, Chat
  also reads `pane.process_info` arguments and stats the shared server's
  control socket, `~/.codex/app-server-control/app-server-control.sock`, to
  warn when Codex runs on that server (`CodexLaunch`).

## Versioned observations

Native Windows machine for the next seven observations: herdr-core 0.1.16 (`e07c2a1`) installed by its own installer, Windows 11 25H2 (10.0.26200), Windows PowerShell 5.1.26100.9711, OpenSSH_9.5p2 for Windows, Node.js 22.19.0, no `DefaultShell` value so sshd's default shell is `cmd.exe`, which these seven did not exercise (2026-11-01, live for #586 on the owner's machine, with the core started from a desktop PowerShell window, medium integrity, and every client running on that machine). None of these seven went through sshd, because no key was installed for SSH then; the SSH exec observations after them say what that later round settled. This is one machine, so check the versions before applying these elsewhere.

- The foreground under PowerShell (method above, `terminal.run` of `choice.exe` and of Claude Code 2.1.286 stopped at its trust dialog with no prompt sent, directly over the pipe, observed through `events.subscribe`, `terminal.get` and a CIM read of the process tree): in each run the core sent one `foreground` event, whose `pid` is the Terminal's, `name` is `powershell.exe`, and `argv` is the absolute `powershell.exe` path followed by the launch arguments as given. It did not name the child, as the source says it cannot (`foreground.rs`: "A pseudo console has no foreground group: this is the terminal's first process"). Under Heeler's form, `-Command "& '<program>' ...; exit $LASTEXITCODE"`, `choice.exe` finished the Terminal with its own code, 2, and that is the only run showing a program's code carried through. Claude Code, stopped by two Ctrl+C keys, left no child of PowerShell and the Terminal finished with 1, whose source is not separated: `claude.exe`'s own code was not recorded, and the keys may have interrupted PowerShell before `exit $LASTEXITCODE` ran. No run had an Agent exit normally. The desktop's form, `-NoExit -Command "& '<program>' ..."`, leaves the Terminal `live` after the program exits, and it finishes only when the shell exits (`exit 5` gave 5). After that exit `terminal.get` shows the same foreground `pid`, `name` and `argv`, and no new `foreground` event came, so the foreground does not tell a running Agent from one that left. That is the foreground, not everything the core reports: in a later `-NoExit` run the attach stream carried PowerShell's prompt after the program exited, recorded only following the paste and 0x03 (the paste observation below). This was not compared as a signal, and `terminal.read` was not read before and after the exit. Other event types were not compared either: the kept `choice.exe` event lines hold one `title` event in each form, naming the `powershell.exe` path, with no timestamp to place it against the exit, and for the Claude Code runs the client kept only `foreground`, `finished`, `status` and `created` events, so seq 13 to 15 and 20 to 22 of that run are lost (no `status` event was among those kept). No other harness was run: `grok`, `opencode`, `pi` and `omp` are not installed there, and Codex was not started. The desktop app itself was not run, only its argv form.
- Frames through `herdr-core connect` (method above; a Node client spoke the same script to `connect` as a child process and directly to the pipe, and the outcomes below were the same on both, though frame counts and reply lengths differed slightly): this run was local, and the crossing is in the SSH exec observations below. Locally, 256 of 256 `terminal.label` echoes came back equal, with request lengths through all 256 low byte values, raw CR, LF, CRLF and TAB between JSON tokens, and UTF-8 lead bytes in values. Reply lengths did not sweep the same way: the 256 replies ran from 585 to 1,049 bytes with one jump of 208 and covered 222 low byte values over the pipe and 208 through `connect` (223 and 211 counting every channel 0 reply). The missing ones include 0x1A (Ctrl+Z), and among the frames recorded through `connect` that low byte appears once, in a separate run's 26-byte attach DATA frame. CREDIT frames for foreign channels carrying all byte values left the link in sync. `connect`'s stderr stayed empty and it exited 0. A `terminal.put` of 6 MiB, in one frame whose base64 alone is 8 MiB, arrived with the same hash. A 3,145,740-byte attach DATA frame of text reached a raw-mode program with the same hash, in about 40 seconds (about 80 KB/s; what sets that rate was not measured), and the link stayed up. With credit withheld a program wrote 6,389,760 bytes (about 6.09 MiB, 98,304 lines of 65 bytes) and a last line: 261,859 bytes came before credit, then 2,195,978 bytes in total with one `CSI 2J`, 33,778 lines, the first and last lines present, two gaps, no close, and a live link. Those counts start at the client's stream handler, set after the attach reply returned, so frames in the same read as that reply are not in them. Program bytes change past the link, in the core or the console, which this run does not separate: on both routes, of attach DATA 0x00 to 0xFF, 0x00 did not arrive, 0x01 to 0x7F arrived unchanged, and each lone 0x80 to 0xFF became U+FFFD, while CR, LF, CRLF and Ctrl+Z arrived as sent. Program output kept UTF-8 and Ctrl+Z, and a bare LF became CRLF. Valid UTF-8 (Chinese and an emoji) in a bracketed paste envelope with CRLF, then 0x03 and `CSI 13 u`, reached a raw-mode program byte for byte. Against Unix this run showed the same codec, not a byte comparison.
- Pipe and `core.lock` checks (method above, in two stop and start rounds, one with an idle holder running): **a plain read of `core.lock` fails while the core runs**, because the core holds byte 0 under `LockFileEx` (`platform/windows.rs`). `Get-Content`, `cmd /c type` and `file.read` report a lock violation (os error 33), `ReadAllText` a sharing violation (0x80070020), Node `EBUSY`, and an SFTP read at offset 0 a Failure. A read from byte 1, with share `ReadWrite,Delete` or at SFTP offset 1, returns the path without its first backslash. After `server stop` by the installer path (exit 0, `{"stopped":true}`) the whole file reads as `\\.\pipe\herdr-core-<user>-<session>.sock` and stays there, the pipe is gone by `Test-Path`, `[IO.File]::Exists` and `GetFiles`, and no `herdr-core` process remains at 1.5 and 16.5 seconds or after `--version`, which starts nothing. Before any core ran there was no state directory at all. Running, the same three checks report the pipe, repeated with no harm to the core and an empty `core.log`. `cmd /c if exist \\.\pipe\x` and Node's `fs.existsSync` said no in both states, so neither can be the check. `connect` reached the same pid and `core.id` as the direct pipe and added only its own process while connected. A holder (a second `herdr-core.exe`, in `server.status`, with no Terminals) appears after the first Terminal and lingers. How these reads behave from an SSH exec's `cmd.exe` is in the SSH exec observations below. Whether the pipe of a core started at medium integrity admits an elevated SSH token is still not observed.
- `terminal.put` (method above, directly over the pipe; through `connect` only the 6 MiB put above ran): the name `note one.txt` was written as `%LOCALAPPDATA%\herdr-core\<session>\files\<address>\note_one.txt`, and a program in the Terminal read it by that path with the same hash. The file, its folder and every parent up to the state root inherit, unprotected, SYSTEM, Administrators and the account at FullControl, and no one else. Exactly 8 MiB was accepted with the same hash; 8 MiB plus one byte was refused with `invalid_params` (-32602), `at most 8 MB per put`. The folder stays after `terminal.kill` and goes with `terminal.rm`. Only that one name was tried for cleaning.
- `HC_TERMINAL_SOCKET` (method above, read in both Node and PowerShell programs inside Terminals): it holds `\\.\pipe\herdr-core-<user>-<session>.sock`, with `HC_TERMINAL_ID` such as `t6`, `HC_SCOPE` set, `TERM_PROGRAM=ghostty` and no `SSH_CONNECTION`. Node's `net.connect` opened it in 1 ms and a plain JSON-RPC `terminal.label` line was answered at 3 ms, with the labels event seen by a subscriber. Addresses are not plain decimal, restart or not: they count over 30 symbols with no vowels and no `l` (`terminals.rs` `address`), and `t19` was followed by `t1b` live with the same core pid. Pi and Oh My Pi themselves were not run: they are not installed there.
- Reading a growing file, for Transcripts (method above; `sftp-server.exe` from `C:\Windows\System32\OpenSSH` spawned locally and spoken to over stdio, **not through sshd**, and made-up files, not a real Agent's): with the writer holding an append descriptor from Node or `FileShare.Read` from .NET, at each of three rounds `file.read`'s line count and last line matched a direct read, and SFTP (`C:/...` and `/C:/...` both open) read as many bytes as its reported size and then reached end of file. **SFTP's content was not compared**: the client discarded the text when a read ended with an EOF status, so only open, size and byte count were kept. Those byte counts equal what the direct read's lines add up to (for example 46 lines came to 396 bytes with LF and 442 with CRLF), which is a check of the count, not of the bytes. With a `FileShare.None` holder both fail: `file.read` with `io` (os error 32), SFTP open with Failure, as Node with `EBUSY`. `file.read` is limited to 8 MiB per read, 64 MiB per file and UTF-8 by source (`files.rs`); no large or non-UTF-8 file was tried over SFTP. The SSH exec observations below compare the content through sshd.
- A paste at PowerShell's prompt (method above, a `-NoExit` Terminal after its program exited, through local `connect`): in the stream the client kept, from the attach reply to the paste about 6 seconds later, there was no `CSI ?2004h`. That window starts after the first paint. The client set its stream handler only once `terminal.attach` returned, so frames arriving in the same read as the reply were dropped, and this run's `CSI ?2004l` was most likely lost that way: a first paint carries one (`data-attach-first-paint` in the vectors, from another Terminal), and the frame tests' kept streams also begin at program output. A first paint can also replay the screen's modes, so this Terminal's first paint is unknown. The run did not record whether the prompt was drawn within the window, and the bytes after the paste were not searched. A bracketed paste of a harmless command, with no Enter, showed on the line and did not run. One byte 0x03 printed `^C` and a new prompt, and the command had still not run. The Terminal stayed `live`, and `exit 6` finished it with 6. Whether a dead Agent's bracketed paste mode stays set in the viewer's emulator was not tried on Windows; ADR 0035 says flags stay behind on Unix, and that would open the mode gate at this prompt. The SSH exec observations below kept the first paint and searched past the paste.

Native Windows machine over real sshd for the next nine observations: the same machine and versions, OpenSSH_for_Windows_9.5 reached with `ssh -T` from a Mac (OpenSSH_10.3p1), no `DefaultShell`, and an exec that ran under `cmd.exe` (`%COMSPEC%` read `C:\WINDOWS\system32\cmd.exe`) with the user's profile as its working folder (2026-11-01, live for #586 on the owner's machine). **Both tokens were elevated.** The SSH token read High Mandatory Level, elevation type default. The core, reported as started from a normal desktop PowerShell, read High (0x3000), elevated, elevation type full, in session 2, from its own process token, and its parent had gone, so how it came to be elevated was not seen. Its holder and Terminals were High too, and a PowerShell Terminal's title began `管理员:`. Each observation is one machine, Windows PowerShell 5.1, an elevated SSH token and this elevated core. Only the stopped-core observation below stops the core, at the end of the round, and no harness ran.

- Exec forms and the pipe check from `cmd.exe`: `%LOCALAPPDATA%\Programs\herdr-core\herdr-core.exe connect --session <s>`, ADR 0031's `.\AppData\Local\Programs\herdr-core\herdr-core.exe connect --session <s>` and the first with both words in double quotes each reached the core. Everything below used the first. With the core running, `powershell.exe -NoProfile -NonInteractive -Command "Test-Path -LiteralPath '\\.\pipe\<name>'"` read `True`, `[IO.File]::Exists` `True`, a `GetFiles` count `1`, and `-EncodedCommand` `True`; for a name with no pipe they read `False`, `False`, `0` and `False`. `if exist \\.\pipe\<name>` in the default shell said `no` for both, so it cannot be the check. These match the desktop results. `dir /b \\.\pipe\` does not list an empty folder: `dir` itself fails with "The parameter is incorrect" in the machine's language and exit 1, so `dir /b \\.\pipe\ | findstr` tells nothing. With two trailing backslashes the default shell can do the check: `dir /b \\.\pipe\\ | findstr /x /i /c:"<name>"` printed the name and exited 0 for the running core's pipe, and exited 1 with empty stderr for a name with no pipe, in eight rounds over two runs; in five of them it also exited 1 for the name with its `.` replaced and for the name without `.sock`, a prefix of the holder's pipe. A failed `dir` exits 1 too, so only stderr tells it from a missing pipe. That is one machine; the stopped core is in the next observation. This guard read `True` before every `connect`: `powershell.exe -NoProfile -NonInteractive -Command "$f=[IO.File]::Open((Join-Path $env:LOCALAPPDATA 'herdr-core\<s>\core.lock'),'Open','Read','ReadWrite,Delete');$f.Position=1;$r=New-Object IO.StreamReader($f);$t=$r.ReadToEnd();$f.Close();Test-Path -LiteralPath ('\'+$t.Trim())"`. Reading the file through sshd's SFTP, the open worked and reported 44 bytes, offset 0 failed with Failure, and offset 1 returned 43 bytes starting `\.\pipe\`.
- A stopped core through the exec: just before the stop the guard read `True`, and `connect` reported the expected pid (running about 90 minutes), `core.id` equal to `core.json`'s, no Terminals, and one holder. `set HC_SESSION=<s>&& %LOCALAPPDATA%\Programs\herdr-core\herdr-core.exe server stop` from the default shell exited 0 with `{"stopped":true}`; there is no space before `&&`, and `set HC_SESSION=<s>&& set HC_SESSION` printed the name exactly. Core and holder were gone at the first read, 0.6 seconds after the exec returned, and at 2.1, 4.5 and 10.7 seconds. **`core.lock` stays** at 44 bytes with no trailing newline and holds `\\.\pipe\herdr-core-<user>-<s>.sock`. Once stopped, its byte 0 reads like the rest: `type`, `Get-Content -Raw`, `ReadAllText`, a read from byte 1 and `scp` (SFTP by default in that client) all succeeded, `scp` returning all 44 bytes and the read from byte 1 the path without its first backslash, so the guard's rebuild of the name still works. **The check reads absent under both shells**, the same about 40 seconds after the stop and from about 34 seconds after `--version`: `dir /b \\.\pipe\\ | findstr /x /i /c:"<name>"` exited 1 with empty stdout and stderr while `dir /b \\.\pipe\\ >nul` exited 0, and a `findstr` for the session name matched nothing; the guard, `Test-Path`, `[IO.File]::Exists` and `-EncodedCommand` read `False`, and the `GetFiles` count `0`, so a client that runs `connect` only on `True` stops there. `-EncodedCommand` also wrote a CLIXML progress record to stderr while still printing `False` and exiting 0, so stderr alone cannot judge that form. No process appeared: `Get-Process` for `herdr-core` and `hc` and `tasklist` found none at each read, including right after `--version` (`hc 0.1.16`, the only subcommand run while stopped, which started nothing) and 31 to 34 seconds after it. The state folder kept `core.json`, `core.lock`, the empty `core.log` and `holder.log`, `terminals.json`, `files` and `screens`, with the same sizes at both reads. No core was started after this stop, and `connect` was not run against the stopped core, so this round does not show what it does there; by ADR 0031 it would start one.
- The elevated token and the pipe: the SSH token entered the pipe, and `hello`, `server.status` and everything below ran, as an elevated client on an elevated core. The pipe read `O:BAG:<group>D:P(A;;FA;;;SY)(A;;FA;;;<account>)S:AI(ML;;NWNR;;;HI)`. **An elevated SSH token also enters a medium-integrity core's pipe**, seen in a later run on a core the owner started from a desktop window that a guard had confirmed not elevated: the core's token read `il=0x2000`, elevation type limited, while the client's read `il=0x3000`. Through `connect`, `hello` and `server.status` answered, pid and `core.id` held, a `powershell.exe` Terminal read `S-1-16-8192` for itself and finished with its own exit code 7, a line typed into an attached Terminal came back on its stream, and `server stop` over the exec answered `{"stopped":true}`, the pipe check then read `False` and no process remained. The frame byte checks below were not repeated on this core, and that pipe's own label was not read (`Get-Acl` failed on it). `pipe_security` in `platform/windows.rs` at v0.1.16 writes the label as `ME` for a core that is not elevated. By the same source, a medium client is kept out of this High pipe with `the Windows core exists but this process cannot access its pipe`; that was not tried.
- Frames across the exec, measured on the raw stream: no byte changed in either direction. As a control with no core, a stdin-to-stdout Node program over the same exec form returned every byte value, a mix of CR, LF, CRLF, 0x1A and 0x00, a leading 0x1A, 8 MiB of random bytes and 8 MiB of repeated byte values with the same SHA-256, with stderr empty and exit 0. Through `connect`, 257 `terminal.label` echoes came back equal, with request and reply lengths each covering all 256 low byte values, which now include 0x0A, 0x0D and 0x1A in frame headers; the recorded streams then walked as frames to their last byte, 133,830 bytes out and 348,443 in. Client frames: the every-byte DATA frame, RESIZE and the first paint, CRLF, UTF-8 frames are byte-identical to the local capture, and what the program read matches both earlier local routes (0x00 gone, 0x01 to 0x7F unchanged, each lone 0x80 to 0xFF as U+FFFD, CR, LF, CRLF and Ctrl+Z as sent), so those changes are past the link, not the exec's. Valid UTF-8 up to four bytes reached the program unchanged. Program output: 0x00 to 0x7F arrived with a bare LF as CRLF, and each lone 0x80 to 0xFF as U+FFFD. A Node program observing the same Terminal directly on the pipe, from another exec, received the same 590 bytes, and the same 6,390,350 bytes (98,304 lines over about 11 seconds, no gap, no `CSI 2J`) as the Mac. A `terminal.put` in one 8 MiB frame arrived with the same hash in 0.4 s and 8 MiB plus one byte was refused. A 3,145,740-byte attach DATA frame reached a raw-mode program with the same hash in 37.4 s, about 84 KB/s, so the exec does not set the rate seen locally. With credit withheld, 6,389,760 bytes written: 262,144 bytes (256 KiB, first paint included) came before credit, then 2,196,263 in total, 33,778 lines, first and last present, two gaps, one `CSI 2J` besides the first paint's, no close and a live link, matching the local run once its uncounted first paint is added. **The same repaint happened with credit granted for every frame**, when the program wrote those 6,390,350 bytes unpaced, ending within about a second: the Mac got 2,196,107 bytes with two gaps while the pipe observer got all of it. A Python client held the Mac end, and what limited it was not separated. Against the Unix vectors (herdr-core 0.1.13, so a comparison across versions): a program's `hello\r\n` is the same 16-byte frame as `data-attach-raw-bytes` on channel 2, a CLOSE for a program's end equals `close-program-ended` except for `finished_ms`, and that vector file's CREDIT, RESIZE, focus, facts and CLOSE frames were sent unchanged, with RESIZE applied (80 by 24) and the link alive. `hello` keys and features and `server.status` keys are the same. `connect` exited 0 with an empty stderr each time stdin closed.
- `scripts/lab/herdr-core-capture.py` from the Mac: through `socat -r -R UNIX-LISTEN:<sock> EXEC:<script>`, whose script runs the guard and then `connect`, it finished with exit 0 and 13 events while Terminals came and went. - Reading a growing file through sshd: **SFTP settled for Transcripts on this machine, with made-up files; no real Agent's file was read.** With a writer in a Terminal (a Node append descriptor, ASCII or UTF-8 lines with CJK and an emoji, or .NET's `FileShare.Read`), five rounds each read the whole file over SFTP, a tail from the last length, and `file.read` through `connect`. Every read was byte for byte a prefix of the final file, and the final file was equal over SFTP, `file.read`, scp and Windows' own `Get-FileHash`. SFTP's size matched its read at each of these rounds, and each read ended with `End of file`. With a `FileShare.None` writer both fail, SFTP's open with Failure and `file.read` with `io` (os error 32). Files sent by scp: non-UTF-8 (GBK, 0xFF, 0x00) is identical over SFTP, while `file.read` answers `not_text`. UTF-8 with a BOM, CRLF, a lone CR, NUL and Ctrl+Z is identical on both. - Node through a junction: the exec refused `<...>\fnm_multishells\<id>\node.exe` with `ERROR_UNTRUSTED_MOUNT_POINT`, while a Terminal of this core ran the same path, directly and from PowerShell. - A styled screen on a core, herdr-core 0.1.13 (`88fe4e7`) on macOS 27 (2026-10-31; source review of `api.rs` `terminal_read`, `api/types.rs` `ReadParams` and `ReadResult`, `viewers.rs` and `crates/ghostty-vt/src/lib.rs`, then a live capture through `scripts/fixtures/herdr-core-ssh.py` with no sign-in and no harness; no Linux run, and no live Agent drew these screens): `terminal.read` has no styled or cell form. Its params are `terminal`, `caller` and `lines`, and its result `text`, `complete`, `how` and `why`, plain text from `screen_text` or the stitch. The Ghostty surface Heeler embeds reads text only too. The process holds no such socket at the prompt, holds exactly one from the sample the file appears in, moves to another at `/new`, and frees it at exit. The hash is not identified (MD5, SHA-1, SHA-2, BLAKE2, BLAKE3 and xxHash forms over that path did not match), so whether a Host can work out the name without running Oh My Pi's code is open. On Unix other than Linux the source uses a `flock` sidecar at that path; that was not run. The process opens the session file later than it writes it: by the first sample with no hold, 6.4 seconds after the file with the first two requests held, and 30 seconds after with all four held, then in the same sample as the title slot filling. So there is a window with a named file, no `fresh` and no open file, and the process already holds the lock in it: there the program's own function refused the lease for the id in the file's name and granted one for an unrelated id. `/new` writes the new file at once, before any prompt, and moves the crumb without `fresh`, the open file and the lock to it, and exactly one is open. The crumb outlives the process, and the next `omp` on the same terminal name overwrites it at startup with `fresh`. Line 1 of a session file is a title slot, line 2 the `type` `session` header. The security scan was not run: with `security.enabled` its preflight refused with `Security scans require a stored OAuth account for fake` and left the crumb alone. Its source (`src/security/coordinator.ts`) calls `SessionManager.create` without suppressing the crumb, and that one call, run live on a reused terminal, did rewrite the crumb to the new path with `fresh`. Whether the scan restores it is not known. Could differ when signed in: the window before the file opens depends on the provider's title model, a stored provider skips the wizard, and only an OAuth account can run the scan.
