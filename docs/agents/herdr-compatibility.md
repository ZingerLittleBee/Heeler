# herdr compatibility observations

Consult this reference for RPC framing, protocol negotiation, subscription
recovery, Agent launch/input, terminal attach, or remote scrolling behavior.
These observations were moved from `CLAUDE.md` without changing their evidence
versions. They are historical evidence, not fresh tests on the installed herdr.

## Current routing

- Unix API and Events use direct-streamlocal; Unix terminals use PTY exec
  ([ADR 0011](../adr/0011-libssh2-direct-streamlocal-transport.md)). Native
  Windows uses `remote-api-bridge` and `terminal session control`
  ([ADR 0018](../adr/0018-native-windows-hosts.md)); Unix forwarding refusal
  never selects the Windows path.
- herdr-core Hosts are a Server Kind of their own, never a fallback for a
  Herdr TUI Host. Each carries one framed connection to its core:
  direct-streamlocal on Unix, `herdr-core connect` over SSH exec on native
  Windows, and connecting never starts a core
  ([ADR 0031](../adr/0031-herdr-core-hosts-connect-without-starting-a-core.md)).
  Their Agents fill the Console's Herdr TUI-shaped models
  ([ADR 0032](../adr/0032-herdr-core-hosts-fill-the-console-models.md)).
- Start with [HeelerSSHTransport](../../Sources/Heeler/Transport/HeelerSSHTransport.swift)
  and [EventsSession](../../Sources/Heeler/Transport/EventsSession.swift) for
  current adapters and recovery. Older symbol names below belong to their
  observation's version; use the [source map](navigation.md) to reach current owners.
- The committed schema is [scripts/herdr-schema.json](../../scripts/herdr-schema.json).
  Generated types describe that snapshot, not every method in every herdr release.
- For native Windows setup or runtime acceptance, use the
  [setup guide](../guides/windows-setup.md) or
  [acceptance checklist](../guides/native-windows-testing.md).
- Chat ([ADR 0024](../adr/0024-native-chat-from-agent-transcripts.md)) reads
  transcripts over SFTP, and OpenCode's session store with a read-only exec
  ([ADR 0025](../adr/0025-opencode-chat-reads-its-session-store.md)), never
  through herdr. herdr supplies the session id, Agent Status, screen reads,
  `agent.prompt`, `agent.send_keys` and `pane.send_input`. For Codex, Chat
  also reads `pane.process_info` arguments and stats the shared server's
  control socket, `~/.codex/app-server-control/app-server-control.sock`, to
  warn when Codex runs on that server (`CodexLaunch`).

## Versioned observations

- herdr-core startup and environment, herdr-core 0.1.13 (`88fe4e7`) and Herdr desktop 0.1.9 (`3e32d75`) (2026-10-30, source review, plus one live incident on a Mac with hc 0.1.13): on Unix every `hc` subcommand except `server stop`, `--help` and `--version` starts a core when none listens, with the caller's environment (`client.rs:73-96`, `platform/unix.rs:20-26`); `--version` exits while parsing arguments (`cli.rs:156-163`). Live: an `hc schema` probe run from an agent session started a core that restored a kept Terminal with that session's variables. Windows refuses an SSH start only for an elevated token while the user has a desktop session (`platform/windows_session.rs:13-27`). A Linux start tries `loginctl --no-ask-password enable-linger` (`platform/systemd.rs:167-191`). A Terminal's environment is the core's minus `TERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` and `COLORTERM` (`api/run.rs:213-235`), minus `SSH_CONNECTION`, `SSH_CLIENT` and `SSH_TTY` (`platform/mod.rs:41,71`), with `TERM_PROGRAM=ghostty` when unset and `HC_TERMINAL_ID`, `HC_TERMINAL_SOCKET` and `HC_SCOPE` added (`api/run.rs:196-209`); anything else the starter had, such as `CLAUDE_CODE_CHILD_SESSION`, `HERDR_*` or `TMUX`, reaches every Terminal. `core.json` keeps the core's id until its state is wiped (`server.rs:92-121`), and `next_id` survives restarts, so addresses are never reused (`terminals.rs:202-208`). A kept Terminal restarts as the core's own shell in its last directory, with `reported` cleared (`kept.rs:75-93`). The desktop app launches agents through `$SHELL -ic '"$@"; exec "$0" -i'`, `command $argv[2..]; exec $argv[1] -i` under fish, or PowerShell `-NoExit -Command` on Windows (`src/window.rs:110-119`, `2218-2236`), and recognizes those forms (`src/programs.rs:268-287`).
- herdr-core status, input and reads, herdr-core 0.1.13 (`88fe4e7`) (2026-10-30, source review; no Heeler runtime test): `terminal.attach` answers `needs_framed` on a plain connection (`api.rs:378-385`). Any status report sets `reported`, which only a kept restart clears; `state=clear` drops the status (`status.rs:99-103`); otherwise the last report outlives its program while the Terminal runs on. A turn ends whenever the root leaves working, into blocked included (`status.rs:3`, `73-79`), and the `turn` event carries the root state (`viewers.rs:171-174`). `terminal.send` and `terminal.keys` wait `HC_QUIET_MS` (3000 ms) after a person's last keystroke and queue per Terminal (`input.rs:64-67`, `154-163`, `247-249`); `send`'s `if` compares the status word only (`input.rs:178-183`). PR #538 reports an isolated probe in which a send outlived its closed bridge and a resend delivered twice. `terminal.interrupt` waits no quiet period and presses the Template's stop key, else Esc when `reported` and Ctrl+C otherwise (`input.rs:262-278`). Input, resize, display facts and focus from a viewer make it the size leader; an observing viewer's input is dropped (`viewers.rs:186-232`). `terminal.read` with `lines > 0` on a full-screen program scrolls it to stitch history (`api.rs:339-345`), so passive reads use `lines: 0`. A plain events subscription's heartbeat carries the global `seq` at its tick and can precede queued events; framed heartbeats go only into an empty channel queue (`server.rs:221-273`).
- herdr-core framed protocol and events, herdr-core 0.1.13 (`88fe4e7`) (2026-10-30, live on a Debian 13 VM with systemd 257 and Python or Node clients written for the test; no Heeler runtime test): `hello` with `generation: 1, framed: true` answers in one plain line, and frames follow: a 9-byte header of channel (u32 LE), kind (u8) and length (u32 LE, at most 16 MiB), with kinds DATA 0, CREDIT 1, CLOSE 2, RESIZE 3 (u16 cols, u16 rows), FOCUS 4 and FACTS 5 (JSON). Channel 0 carries RPC, whose replies can arrive out of order and match by id; each `events.subscribe` and `terminal.attach` takes the connection's next channel from 1. A stream starts with 256 KiB of credit; client input needs none, and RESIZE or CREDIT payloads that are not 4 bytes are ignored. A backlog over 4 MiB repaints an attach, or sends `missed` and then a snapshot on events. Every domain error is -32000, told apart by `error.data.kind`. A plain connection takes several requests in sequence until `events.subscribe`, then carries only notifications. The subscribe result is the snapshot (`seq`, `terminals`, `channel`). Event kinds seen: `created`, `size`, `title`, `foreground` (`argv`, `cwd`, `name`, `pid`; absent from the subscribe description, `api.rs:131`), `status`, `turn` (`turn`, `state`), `labels`, `keep`, `doc`, `lost`, `restarted`, `finished` and `removed`. `seq` is global, restarts at 0 with each core process and cannot be resumed; the core id and each Terminal's turn count survive restarts. Framed heartbeats come every 15 s from subscribe, skipped only when the queue is not empty at the tick. An attach's first paint turns modes off and then on again (2004 included), and the same repaint can arrive mid-stream after a backlog or a stitched read.
- herdr-core viewers, status and input, herdr-core 0.1.13 (`88fe4e7`) (2026-10-30, live on a Debian 13 VM with systemd 257 and Python or Node clients written for the test; no Heeler runtime test): gaining focus, input, resize, FACTS, and an empty DATA frame each make a viewer the size leader; an observing viewer's input is dropped; with no viewer left the Terminal returns to 200x120. An attach with `resumed: true` defers only to an active viewer. The foreground is sampled every 500 ms (`HC_FOREGROUND_MS`), and a program's first status report arrived 30-465 ms before the foreground event naming it; reports carry no pid or time. `state=clear` drops the status and ends a turn with state null, and `reported` stays true. The turn count also moves on entering blocked or error and on Codex's start-up blip; blocked to done brings no turn event. Input sent during a stitched read arrives about 1 s later, with no echo meanwhile, and aborts the read (`complete: false`). `terminal.interrupt` answered `stopped` both for Pi, which stayed, and Codex, which exited, and in a Terminal that never reported it waits out its timeout (10 s by default). Under bash, 2004 is on only at the prompt. A program that set kitty keyboard flag 8 expects Enter as `CSI 13 u`. A paste whose bytes the program never read reached the shell's readline after the program exited, and a stale foreground check let Enter run it there.
- herdr-core kept Terminals, notes and wrappers, herdr-core 0.1.13 (`88fe4e7`) (2026-10-30, live on a Debian 13 VM with systemd 257 and Python or Node clients written for the test; no Heeler runtime test): a signal to a kept Terminal's program brings `lost` (with no foreground event clearing the old program), then `restarted` about 1.5-2.5 s later with the core's `$SHELL` (no `-i`) in the last directory; labels and the turn count carry over, `reported`, status and title clear, and the attach is closed. A program that exits with a code, `exit` in a wrapper shell included, ends a kept Terminal for good. When a child Terminal exits, the core types its last 20 lines and Enter into a parent with `reported`, live and not blocked; with the desktop wrapper's shell left after the Agent exited, that shell ran the lines as commands. Under fish the agent shares the wrapper's process group, so the foreground keeps the wrapper's pid and only its `argv` changes. Debian's `/bin/sh` (dash) does not exec `sh -c`, so a Template's foreground is `sh -c <line>`; zsh with no startup files stops at its new-user wizard. A child started with `hc run` gets the core's environment, not its parent shell's. Templates live at `$XDG_CONFIG_HOME/herdr-core/templates/<name>.md` (front matter `command`, `ready`, `submit`, `stop`, `paste_gap_ms`); the record carries `template`, `submit` and `stop`, and `terminal.run` with a Template blocks up to 35 s for its first report. A launch request cannot unset a variable: an empty value sets it to the empty string. Launched as `bash -ic 'exec "$@"' bash <program>` or `fish -ic 'exec $argv[2..]' fish <program>` with `keep: true`, the program held the Terminal's root pid and was its foreground, with no wrapper arguments, at the first sample; the Terminal finished with the program's exit code, and after a SIGKILL it restarted as `/bin/bash` with `reported: false`.
- herdr-core on Linux, herdr-core 0.1.13 (`88fe4e7`) (2026-10-30, live on a Debian 13 VM with systemd 257 and Python or Node clients written for the test; no Heeler runtime test): `hc` runs the core as a transient user unit `hc-serve-<8hex>.service` (`systemd-run --user`, `KillMode=process`), and Terminals live in `hc-hold-<8hex>.service`. An SSH caller's `SSH_AUTH_SOCK`, `DISPLAY`, `DBUS_*` and `XDG_SESSION_*` are replaced by the user manager's values while `MOTD_SHOWN` and `LOGNAME` pass through, and a core started from a plain SSH exec gives every later Terminal `PATH=/usr/local/bin:/usr/bin:/bin:/usr/games`. When a core dies with live Terminals, the holder starts a new one after about 3 s (`HC_HOLDER_GRACE_MS`) with the original starter's environment. `server start` on a running core changes nothing (compare `uptime_ms`); its stdout is JSON when not a tty. `bash -lic` over a tty-less exec works but prints job-control warnings on stderr. A plain SSH exec's `PATH` lacks `~/.local/bin`, where the installer puts `herdr-core`, linking `hc` only when that name is free. `core.lock` (the socket path, no newline) exists only after a session's first start and stays after a stop; the default socket is `/run/user/<uid>/herdr-core/<session>.sock`; an SSH channel to a missing, refused or forbidden socket fails with the same message. A blank or whitespace `HC_SESSION` is the default session and names are trimmed; a name whose socket path exceeds 107 bytes, `a/b`, `..` and `a:b` are refused. The core id is per session and state directory, so another `XDG_STATE_HOME` gives another id behind the same socket. A systemd user unit's `PATH` is `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`; `Restart=on-failure` does not restart after a clean exit or SIGTERM; `systemctl --user` over SSH exec needs `XDG_RUNTIME_DIR` (set by `pam_systemd`, else `/run/user/$(id -u)` suffices) and `-M user@` is denied. Debian 13's polkit allows `loginctl enable-linger` for oneself without a password.
- Program Status from harnesses in herdr-core Terminals, herdr-core 0.1.13 (`88fe4e7`) (2026-10-30, same VM, isolated config directories, no sign-in; Claude Code and Codex against a local mock API, OpenCode 2.x from source only): Claude Code reports from 2.1.295; 2.1.314 reported idle, working, done, blocked (permission or question, with `msg`), error, and clear on exit, and done and error stay until the next prompt. Before sign-in it queries but reports nothing until exit, so `reported: true` with no status occurs. Its `sessions/<pid>.json` (2.1.288 and 2.1.314) appears only at the prompt, with only `<pid>.<hash>.key` before; `procStart` is `/proc/<pid>/stat` field 22; its own status (idle, busy, waiting, plus `waitingFor`) cannot tell done or error from idle; the entry follows `/clear` and `/resume`. `CLAUDE_CODE_CHILD_SESSION` suppresses both the entry and the Transcript, and blank `CLAUDE_CODE_CHILD_SESSION` and `CLAUDE_CODE_SKIP_PROMPT_HISTORY` read as unset (2.1.288). Codex reports from 0.163 and done and blocked from 0.164 (0.166.0 tested): no `msg`, never a query, any key turns done or error into idle, and a working blip at start moves the turn count. OpenCode 1.19.5 (npm `opencode-ai`, and `opencode.ai/install`) reports nothing and its `-s` only continues a session; 2.1 and later (`opencode.ai/v2/install`, `@opencode/cli` 2.2.2) report idle, working and blocked with child records keyed by session id, never done or error, and `-s ses…` names a new session created at its first prompt. - herdr-core 0.1.13 (`88fe4e752debdc6ff6689eaa153d7f95819835a4`) and herdr-app 0.1.7 (`941cd3af`), source review during PR #538 unless a live probe is named below: core's JSON-RPC generation is 1; desktop app version and core version are independent. `terminal.list` returns full terminal records, while `hc ls` transforms them into compact CLI output. `foreground` describes the current process separately from launch `argv`. Starting a core terminal does not itself put it in a desktop pane.
- Core identity and input on those versions: a program's last OSC 7501 status can survive its exit when a desktop wrapper continues as an interactive shell. An isolated 0.1.13 CLI probe retained `app=claude-code,state=idle` with foreground `[/bin/sh,-i]`, and a submitted marker command executed in that shell. `terminal.send` (`api.rs`, `input.rs`) waits for human-input quiet, then pastes and presses Enter; its optional `if` tests status, not PID or program identity. Closing the connection does not cancel queued work. A second isolated probe closed a bridge after a send exceeded 15 seconds, sent the same marker through another bridge, and observed two deliveries when human typing stopped. These demonstrate upstream behavior, not an on-device Heeler reproduction. Other dispatched core mutations with an uncertain outcome must not be automatically replayed.
- Core screen reads on 0.1.13 (`api.rs`, `stitch.rs`, `viewers.rs`): `terminal.read lines=N` means up to N history lines in addition to the current screen. Any positive value on an eligible idle/blocked alternate-screen program can acquire its input queue, inject mouse-wheel events, withhold viewer output and restore the view afterward. The scroll budget defaults to 15 seconds and restoration has a separate deadline. Human input interrupts further scrolling but is held until restoration completes; this is not a guaranteed 15-second key delay. Heeler's core screen reads use `lines: 0`, including automatic snippets, so previews remain passive.
- Core status/events on 0.1.13 (`status.rs`, `viewers.rs`, `api.rs`): `error` is a supported root state and, like `blocked`, marks a program stuck; Heeler preserves Error wording rather than treating it as an approval dialog. A status event is emitted for every report, including child records and progress with unchanged root state. The core subscription already includes every local terminal. Heartbeats carry the global sequence and may arrive before queued events with lower sequences; they are not delivered-event watermarks. Heeler ignores unchanged state/app/title reports for refresh scheduling, applies terminal-title deltas locally, and requests fresh inventory after missed events.
- Core CLI boundaries on 0.1.13 (`client.rs`, `attach.rs`, `config.rs`): `connect` auto-starts a core if no listener exists for the selected session, so a wrong session can produce a healthy but empty inventory. `attach` consumes its configured control chord as raw, kitty or modifyOtherKeys input, default Ctrl+backslash, truncates input at that chord and closes the viewer; the remaining bytes in that chunk are discarded. There is no disabled or literal-chord mode in that release. A configured Ctrl+C chord therefore prevents normal interrupt through that attachment.
- Core launch environment on 0.1.13 (`api/run.rs`, `platform/mod.rs`, `platform/systemd.rs`, `platform/unix.rs`): a child gets the daemon environment plus request `env`, using `env_clear` before that map is applied. Linux refreshes selected session variables from the user manager, but not PATH; macOS does not rebuild a login-shell PATH. Finding an absolute Agent script in an expanded SSH PATH alone does not ensure its `env`-based runtime exists in the daemon's PATH. The program-recognition scope remains the documented supported coding programs, not arbitrary reported app names.
- Codex shared daemon and session identity, Codex CLI 0.161.0 with herdr 0.9.3 and Codex integration v8 (2026-10-08, live process environments and `agent.get`, plus isolated replay of the installed hook): a CLI window can inherit its own `HERDR_PANE_ID` while the shared daemon retains another window's value. The installed session hook reads that environment value, so an installed integration does not establish that the current pane has received its session ID. Replaying identical session input against a temporary socket with the daemon and CLI environments selected different panes; the original failing hook invocation was not captured. Codex source at `822e58cc3d` documents this shared-environment limitation in `codex-rs/app-server-daemon/README.md`; `codex-rs/hooks/src/registry.rs` snapshots the daemon environment. An exact, independently verified thread ID can be reported to its verified pane with herdr's `pane report-agent-session` command as a one-time recovery, but this does not repair later new/resumed sessions. Heeler must keep missing identity distinct from installation status or query failure, and must not infer identity from a working directory or the newest transcript.
- Codex shared daemon and session identity, Codex CLI 0.164.0 with herdr 0.9.5 and Codex integration v10 (2026-10-25, source review of Codex `rust-v0.164.0-alpha.11` and herdr `v0.9.5`, read-only live checks, and isolated `codex app-server` runs with a temporary `CODEX_HOME` and no model): the shared-daemon limitation is unchanged (upstream: openai/codex#48500; client env for hooks proposed in openai/codex#44902; herdr tracks it in herdrdev/herdr#4649 and #4814), and no Heeler-side exact mapping exists. Hooks still snapshot the daemon environment (`hooks/src/registry.rs:83`); hook input, `thread/start` and `ClientInfo` carry no client identity, and no app-server method maps a connection to its threads. Environment-scoped hooks (#56304) first ship in `rust-v0.165.0-alpha.1` and accept only owner-submitted managed hooks. Rejected as inexact: terminal title (thread id truncated to 29 characters), status-line or `/status` screen reads (a composer draft can hold the only UUID on screen), a per-pane JSON-RPC relay through `codex --remote` (subagent selection and task tools start or resume threads on the same connection, and switching back to a live thread sends no request), and the TUI's `codex_tui` MCP origin (it identifies the threads a TUI owns, not the one it shows). `[features] daemon_auto_start = false` only stops auto-start; the TUI still joins a running daemon. Only `--no-daemon` keeps hooks in the pane's process, and herdr's restore launches `codex resume <id>` without it (`src/agent_resume.rs:213`). Restore types that command into the pane's shell (`src/app/agent_resume.rs:299`), so a shell alias `codex='codex --no-daemon'` covers it; Codex 0.164.0 rejects the flag given twice ("cannot be used multiple times"), so with the alias users type plain `codex resume`. Even with `--no-daemon`, SessionStart runs only at a thread's first turn (`core/src/session/turn.rs:340`), so herdr keeps the previous id after `/new` or `/resume` until a prompt; herdr rejects Codex's `fork` SessionStart as a replacement (`src/terminal/state.rs` `session_report_allows_session_replacement`), and resuming a thread still loaded within the 1800 s unload delay queues no SessionStart at all.

Rediscovering these is expensive. Each fact retains its evidence version and method (live observation or source review); older observations are not re-tests on a newer release. For 0.9.0 subscription ordering, compatibility evidence, and remaining verification, read [the integration review](../research/herdr-0.9.0-compatibility.md).

- The herdr API socket serves **one request per connection** (read one line, write one line, close). Only `events.subscribe` keeps the connection open. Plan channel usage accordingly. (Re-verified live on 0.8.0: a second write on a served connection gets `EPIPE`. `pane.graphics.stream`, previously listed here, does not exist in the 0.8.0 schema — graphics methods are `pane.graphics.set`/`clear`/`info`, all one-shot. 0.9.0 and 0.9.1 accepted `pane.graphics.stream` although their schemas omit it, and kept its connection open for image frames; 0.9.2 removed the graphics API, so all four methods answer `unknown_method`: source review at `v0.9.0`, `v0.9.1`, `v0.9.2` and `v0.9.4`, and the 0.9.2 release notes.) Since 0.9.2, `server.ssh_agent.register` also holds its connection on Unix: herdr answers `ok`, then keeps the connection open until the client closes or writes to it, or the server stops (source review of `src/api/server.rs` at `v0.9.2`; live on isolated 0.9.3 and 0.9.4 backends, still open 2 s after the reply). Heeler does not call it.
- Wire format: request `{"id": "<any string>", "method": "...", "params": {...}}` + `\n`; `params` is required, and `{}` satisfies it. Success `{"id", "result"}`, failure `{"id", "error": {"code", "message"}}` (both re-verified live on 0.8.0), subscription event lines `{"event", "data"}` with no id.
- The first message on any new connection path should be `ping` — it returns the server protocol version (0.8.2 answers `{"version":"0.8.2","protocol":20,...}`; 0.8.0, verified live, answered `{"version":"0.8.0","protocol":19,...}`). herdr's API has no stability guarantee; parse leniently (ignore unknown fields). The app enforces a **floor**, not equality: `HeelerSSHTransport.minimumProtocolVersion` refuses older servers, `generatedProtocolVersion` only drives an advisory notice. Equality here made every 0.8.0 Host unusable (#140) — do not restore it.
- The API schema is exported offline via `herdr api schema --json` (JSON Schema 2020-12): the binary prints the schema built into it and contacts no server, while a bare `herdr api schema` prints only a summary (source review of `src/cli/api.rs` at `v0.9.4`). Its `$ref` paths are non-standard nested (`#/schemas/request/$defs/X`) — preprocess before feeding codegen tools. The committed snapshot is the 0.9.4 export (protocol 22), byte-identical to 0.9.3's. It declares 102 request methods, as 0.9.0's did, but not the same ones: 0.9.1 added `pane.link.resolve`, and 0.9.2 added `pane.clear` and `server.ssh_agent.register` and removed `pane.graphics.set`/`clear`/`info` (diffed against the 0.9.0 snapshot; versions from source review of `src/api/schema.rs` at `v0.9.0`, `v0.9.1` and `v0.9.2`). It declares 26 event kinds, and every one of those kinds has a typed `EventData` variant; separately, 3 pane-scoped kinds (`pane.output_matched`, `pane.agent_status_changed`, `pane.scroll_changed`) have typed `SubscriptionEventData`. The event kinds, their `EventData` variants and the subscription-event schema are unchanged from 0.8.2, but the event schema's `PaneInfo` gained an optional `restore_error` in 0.9.2 (diffed against the 0.8.2 and 0.9.0 snapshots; the version from source review at `v0.9.1` and `v0.9.2`). Payloads herdr actually emits are still worth verifying empirically.
- Pane ids are opaque strings. Protocol-22 `scripts/herdr-schema.json` declares `pane_id` as a string with no `pattern`. Observed herdr 0.7.5 captures (`w1:pA`, `w3:pB`, `wV:p1`) and live 0.8.0 `agent.list` samples (`w1:pT`, `w1C:p1`, `wR:pC`, `wV:p1H`) are alphanumeric `w…:p…` identifiers and include uppercase letters. Those captures contain no tmux-style `%N`; that does not prove herdr can never emit it. Treat every pane id as an opaque string; do not parse or validate a grammar.
- SSH exec channels are session channels, capped by sshd's `MaxSessions` (default 10) per connection. All RPC traffic must go through a request queue that bounds concurrency.
- `herdr agent attach` requires a TTY (ratatui). It works over an exec channel only when a PTY is requested.
- herdr 0.7.5 tightened `agent.start` (verified against a live 0.7.5 server): the kind must be on its supported-agent list (arbitrary commands like `bash -i` are rejected with `unsupported interactive agent kind`), and a freshly created pane is rejected with `agent_pane_busy` ("not an available shell") until its shell reaches the interactive prompt, a few seconds. On 0.8.0 and later the start is asynchronous: an accepted start returns `launch_pending: true` at once (verified live on 0.8.0, 6ms after pane creation). herdr still answers `agent_pane_busy` while a startup command holds the fresh pane's foreground, so the retry is required, not 0.7.5 compat: live on 0.9.3, a zsh whose rc runs `/bin/sleep 1` was refused until about 1.2 s (spec #449's verification rounds; their output was not saved), and live on 0.9.4, fish with Homebrew vendor configuration drew 146 `agent_pane_busy` and 2 canonical refusals before its launch went through at about 2.4 s (probed every 10 ms). On a macOS Host, 0.9.4 also refuses a launch line longer than the terminal's canonical input limit (1,024 bytes) until the shell's line editor starts, with `agent_start_input_failed` and "input contains a N-byte line but the terminal is in canonical mode with a 1024-byte limit; wait for the shell prompt and retry", where N is the UTF-8 length of the shell-quoted command line plus Enter (verified live on 0.9.4 with a 1,100-character ASCII argument and a CJK one). The refusal reserves no name and queues no input (live, and the v0.9.4 source checks before either), so resending the same request is safe. Live on 0.9.4, such a launch went through within about 0.1 s in bash, a bare zsh, ksh and tcsh, after about 2.4 s in fish, and never in dash, even at its prompt. - Server lifecycle, herdr 0.9.3 and 0.9.4 (live on isolated default and `work` servers while implementing #457 unless marked otherwise; source review of `src/platform/unix_common.rs` `ignore_server_hangup` and `spawn_server_signal_monitor`, `src/server/headless/lifecycle.rs` `complete_shutdown` and `cleanup_sockets`, `src/api/server.rs` `ServerHandle` and `src/persist/restore.rs` at `v0.9.3` and `v0.9.4`): from 0.9.4 a Linux or macOS server ignores `SIGHUP` and logs "ignoring SIGHUP; server keeps running", so closing the shell that started it no longer stops it (release note #4920, #4965); 0.9.3 quits on `SIGHUP` (its `ctrlc` handler enables the `termination` feature) and removes its sockets. On a macOS restart or shutdown, 0.9.4 takes the same quit path as soon as loginwindow announces it past its point of no return, instead of waiting for launchd's `SIGTERM` (`HostShutdownMonitor` in `src/platform/macos/shutdown.rs`; source review only; release note #4414, #5013, #5057, #5092). A server started again after a stop restores the same Workspace, Tab and Pane ids and gives every Pane a new terminal id (`TerminalId::alloc`): Tabs `w1:t1` and `w1:t2` with Panes `w1:p1` to `w1:p3` came back with the same ids and three new `term_…` ids on both versions, and `herdr terminal attach` with a pre-stop terminal id then failed with `terminal attach failed: terminal term_… not found`. Heeler follows the new terminal id where it keys by Host and Pane (source review): Agent rows (`ConsoleAgent.ID`), Agent Attach (`TerminalAttachTarget.agentPane`; `AgentTerminalCache.reconcile` evicts an entry whose terminal id changed) and Workspace Terminals (`ConsoleTerminal.ID`, whose terminal id is re-read from each snapshot and reconciled by `TerminalConnectionPool.reconcile`). Agent detail's Open Terminal does not: it reuses the `ShellTerminalIdentity` that `ConsoleStore.shellTerminals` keeps across reconnects once `HostConsoleProjection.paneExists` finds the Pane id, so after a restore it can reattach to the pre-stop terminal id (static reading, not run).
- Unreachable sessions, herdr 0.9.4 (live on an isolated server while implementing #457, with `chmod 000` on a running default session's `herdr.sock` standing in for a refused connection; source review of `src/session.rs` `session_info` and `src/cli.rs` `server_not_running_error` and `print_session_table` at `v0.9.4`; release note #4717, #4769, #4777, #4779): `herdr session list --json` reports `running` only when it can connect, and adds `connection_error` (omitted otherwise) when the connect fails for any reason other than a missing socket or a refused connection, for example `{"name":"default","default":true,"running":false,"connection_error":"Permission denied (os error 13)"}`. The table shows that session as `unavailable`, with the error on the next line. 0.9.3 has no such field and lists the same session as `stopped`. On Windows, a pipe that refuses the client (see the named-pipe bullet below) is reported the same way; herdr's Windows-only test `session_discovery_distinguishes_denied_running_and_stopped_servers` covers it. Heeler's `HerdrSession` decodes only `name`, `default` and `running`, so the Host's Available Sessions list shows an unavailable session as Stopped and, unless it is the default session, will not select it (source review of `HostOnboardingView.availableSessionsSection`).
- Subscription overflow, herdr 0.9.2 and later (source review of `src/api/subscriptions.rs` `subscription_events_after` and `src/api/event_hub.rs` at `v0.9.2` and `v0.9.4`, absent at `v0.9.1`; herdr's socket API documentation at `v0.9.4`; release note #4178, #4225; not reproduced live): every subscription reads one shared history of the last 512 events, and a subscriber that falls behind it gets one error line carrying its `events.subscribe` request id, `code: "events_lost"` and "event subscription fell behind retained history; resubscribe and resync with session.snapshot", after which herdr closes that connection. Before 0.9.2 such a reader skipped the lost events silently. Heeler recovers through its ordinary reconnect (source review): `HerdrWire.decodeEvent` drops the error line, `runEventsChannel` reports the close as the retryable `channelFailed("events channel closed by remote")`, and `EventsSession` reconnects with backoff, resubscribes and takes a fresh `session.snapshot` once `.connected`. Heeler's own `.eventsDropped` marker is unrelated: it reports an overflow of Heeler's local event buffer.
- `agent.focus` effects, herdr 0.7.5 to 0.9.4 (live on isolated 0.9.3 and 0.9.4 servers while implementing #457, with statuses reported through `herdr pane report-agent` and a `herdr` client running on a PTY; source review of `src/app/agents.rs` `focus_agent_target` at `v0.7.5`, `v0.8.2` and `v0.9.4`, of `src/server/headless/client_views.rs` at `v0.9.0` and `v0.9.4` (absent at `v0.8.2`), of `src/api/subscriptions.rs` at `v0.9.0` and `v0.9.4`, and of commit 985d3442 (#3764), which is in 0.9.1 and not in 0.9.0): the call makes the Agent's Tab the server's active Tab, focuses the Agent's Pane and marks every Pane in that Tab seen, so Done Agents there read Idle (two Done Panes in the focused Tab both turned Idle). herdr emits no status event for this (`mark_active_tab_seen` only sets `seen`, so plugin hooks and other event readers see nothing), but a Pane-scoped `pane.agent_status_changed` subscription falls back to polling its Pane and delivered Idle for both Panes within 60 ms, next to `tab_focused` and `pane_focused`. Later completions in that Tab read Idle instead of Done while no herdr client is attached or the attached client's terminal reports focus (`active_tab_suppresses_notifications`); live, with no client attached, a completion in the focused Tab read `idle` and one in another Tab `done`. On every supported herdr except 0.9.0 the call also moves attached herdr clients, and their next keystrokes, to that Tab: 0.7.5 to 0.8.2 share one view between clients, 0.9.0 gives each client its own view and does not project agent focus onto it, and since 0.9.1 `focus_all_shell_clients_on_default_target` moves every herdr UI client (release note #3760, #4153, #4171). Live, text typed into the attached client went to the first Tab's Pane before the call and to the focused Agent's Pane after it. The projection moves only herdr's own UI clients (`ClientConnectionMode::ClientShell`); a direct `agent attach` or `terminal attach`, which is how Heeler attaches, stays on its terminal (source review at `v0.9.4`).
- Windows named-pipe access, herdr 0.9.4 (source review of `src/platform/windows.rs` `local_server_security_descriptor` and `local_server_connection_error`, `src/ipc.rs` `bind_local_listener`, `src/cli/server.rs` and `src/server/headless/bootstrap.rs` at `v0.9.4`, and of herdr's `windows-beta` documentation at `v0.9.4`; release note #4717, #4769, #4777, #4779; not exercised on a native Windows Host): a server's named pipes grant SYSTEM full access and the server's own account read and write, and nobody else. When the server's token is elevated, a High integrity label also refuses that account's ordinary (medium-integrity) processes, so only administrator terminals can connect; herdr's documentation notes that this includes a server started through an elevated SSH login. A server started with `herdr [--session <name>] server --allow-unelevated-clients`, or while herdr's config sets `[server] allow_unelevated_clients = true`, uses a Medium label and admits both. The setting is read when the server starts, so reloading config does not change a running server, and other accounts stay excluded. A refused client's error begins "For an elevated server, use an administrator terminal" and names the flag, and `herdr session list` reports the session with `connection_error` (see the unreachable sessions bullet above). The [Windows setup guide](../guides/windows-setup.md) therefore leaves the scheduled task's highest privileges cleared and starts the named session from a normal terminal.
