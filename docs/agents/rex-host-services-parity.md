## A Rex status report and the foreground banner

On November 27, 2026 a private Rex `0.1.0-preview.25` server (`b070aae645f5`, advertised API 24) ran on macOS 27.0.1 arm64. It used its own Unix socket, home, XDG directories, empty configuration, state directory, and `--restore=false`. An inert shell in one `heeler-lab-` session wrote OSC 7501 reports. The shipping CLI followed only that session with `rex --autostart=false -S <lab-socket> events -s <lab-session> --json`. The fixture captured the following six root reports in order. Session IDs, block IDs, process IDs and exact timestamps are omitted. [Rex Program Status][upstream-protocol] · [Rex event fields][upstream-events] · [Heeler's stand-in fixture][status-live]

```text
envelope      session_event / block_event / program_status_changed
record        id=""  reason=report  app=codex  effective_app=codex  owner={pid,name}
observed      working → blocked → working → done → done → error
timestamps    6 distinct updated_at values, including both consecutive done reports
cleanup       sessions=[] on the private socket before server shutdown
```

A second run stopped the subscriber, emitted Working, Blocked, then Done, and queried the terminal's `program_status`. It returned one current Done record. A fresh subscription received zero of the three elapsed transitions and saw the next Working report. The fixture again left zero sessions. Both CLI observations end at the Rex interface. Heeler negotiates revisions 12–19 at this baseline. Its control client reads the root status, validates the foreground process identity, and maintains this device's turn and seen state. Child status reports and a previous foreground's surviving result do not identify a new completion. A repeated Done can have a new timestamp for the same turn. Agents with no qualifying status read Unknown. The earlier live Swift fixture covers these inventory and turn checks. An existing Console regression uses a scripted server and asserts both a visible Done count and a nil banner. [Negotiation and live results][versioned-rex] · [Agent rule and seen state][turn-adr] · [Console regression][negative-banner]

Heeler's app model feeds the same Agent list to the banner store for every Server. The store takes first sight as its baseline, waits three seconds for a transition to hold, suppresses the Agent already visible in the key window, then reads the Host's trigger preferences. Blocked and Error use `blocked`. Done uses `done`. A presented banner expires after five seconds. Tapping dismisses it and passes the Host UUID and opaque pane ID through the scene router to Agent detail. A Rex pane ID includes the escaped session and block IDs. None of that foreground rendering or routing needs an APNs token. [App observer][banner-root] · [Preference wiring][banner-wiring] · [Hold and trigger][banner-store] · [Tap][banner-tap] · [Scene selection][scene] · [Route][router] · [Rex pane ID][rex-address]

The missing part at the baseline is consent for a **Rex foreground banner**. The existing Settings → Notifications → Hosts section requires a push token and lists integrated Hosts. Its Notifications switch writes a remote registration. Enabling it creates explicit `blocked=true` and `done=true` flags. Done Notifications updates the latter. Turning Notifications off removes the registration and local key. A foreground-only Rex design can reuse the banner and its click path with a separate per-Rex-record device preference on the same page, visible without a push token. Default it off, return no trigger when off, and label the enabled scope as *while Heeler is open*. Removing the Rex record should discard that preference. Check the actual scene state when a hold fires. The connection coordinator remains effectively active for up to 15 seconds after entering the background. [Scene changes][scene-phase] · [Connection grace][connection-grace] · [Settings entry][settings-entry] · [Token gate][notification-ui] · [Registration writes][registration-writes] · [Flag defaults][flag-defaults] · [Existing view model][notification-host]

For the Herdr comparison, `npm test -- test/notify-hook.test.js` in `plugin/` ran 34 tests on Node 24.11.0. All 34 passed, including per-device decryption, a status that changed during the hold, duplicate suppression, and removal of an expired token. It ran the real hook process against a stub Herdr status read and a loopback HTTP receiver with fixture keys. No APNs gateway, Notification Service Extension, Lock Screen, or backgrounded iPhone was exercised. The upstream Rex documentation describes indicators for its own session picker and tabs. Its Lua event handlers run inside a live `rex do` process. A handler placed in `init.lua` does not run. ## Candidate foreground banners

In the candidate, open **Settings → Notifications → Rex In-App Banners**. Each saved Rex Server identified as macOS or Linux has its own switch, labeled with its display name. A native Windows pipe, Windows kernel, and unidentified platform have no Rex banner control. The projection applies the same gate before accepting a report. If platform evidence becomes temporarily unavailable, the device retains the choice until that Server is identified again. Every switch starts off. Turning one on enables Blocked and Error. **Include Done** starts off and adds finished turns for that Server. Turning the Server switch off or removing its record clears the choice. The dictionary `notifications.rexForegroundBanners` in this device's defaults maps the saved Host UUID to the Include Done flag. An absent entry means off. These settings are available before the device obtains an APNs token. They write only device defaults. [Settings controls](../../Sources/Heeler/Settings/NotificationSettingsView.swift) · [Preference storage and catalog removal](../../Sources/Heeler/Notifications/NotificationPreferencesStore.swift) · [Preference regression](../../Tests/HeelerTests/NotificationPreferencesStoreTests.swift)

The first status after activation, a new connection, a different foreground, or an inventory read that discovers an unobserved change establishes a baseline. The subsequent matching Agent transition must hold for three seconds while an app window is active. A duplicate report or an Agent already on screen stays quiet. The existing banner shows the workspace, Agent kind and status and dismisses after five seconds. A tap checks the instance, connection generation, continuous report history, session/block address and foreground. A fresh Rex `process` read must still identify the captured PID and Agent kind before scene routing opens the Agent. Rex's `process` response supplies no process start time. A process that reuses both the PID and program name without an intervening observable change cannot be distinguished by that response. ## Where additional support belongs

A connected Rex listener already has the information needed for an observed Blocked or Done transition. A Host-side Rex listener can feed the Host Helper's existing registration reader, per-device trigger rules, envelope encryption, Push Relay transport and token revocation. It would need to associate each registered device with the intended Rex Server, bind the report to its current foreground, and preserve turn/seen state through reconnects. The shipped service starts core and tmux listeners. An explicitly installed, enabled and versioned Rex listener, the registration UI, and a delivery test through the APNs gateway are separate deployment work. For Lock Screen Live Activities, the app must also start an Activity and provide its per-Activity push token, while the listener must issue updates and end it. The foreground defaults contain neither a device token nor an Activity token. [Host Helper entry point][helper-main] · [Trigger and delivery pipeline][notifier] · [Registration files](../../plugin/helper/shared/delivery/registrations.js) · [Push transport](../../plugin/helper/shared/delivery/push.js) · [Encrypted notification envelope](../../plugin/helper/shared/notification-envelope.js) · [Activity token lifecycle][activity-contract]

- **Changes and Skills on POSIX.** The candidate reuses the SSH git reader and skill cache for explicit project reads. Background row totals have a separate capability because they would run while the list is visible. A Server that can read a Changes document does not thereby receive the generic Host service's git mutation or harness-edit operations. [Candidate read callers](../../Sources/Heeler/Console/ConsoleStore.swift) · [Host services contract][host-services] · [Rex project reads](../../Tests/HeelerLiveTests/RexProjectLiveTests.swift)
- **Reports missed by every listener.** Rex would need replay from a durable cursor to recover their order. A persistent per-block completed-turn counter would answer the narrower question of how many turns finished. Resync in preview.25 recovers only the current report. [Event resume][resume-adr] · [Turn observations][turn-adr]
- **Usage and widgets.** A Rex-capable Host collector or an explicitly configured shared collector would need to produce readings for the existing Usage schema, name the account roots, respect limit-reader consent, and count each machine once. Current core/tmux recorder adapters demonstrate the host-side inputs. The first-party Rex status report contains terminal program state. It has no token-accounting or provider plan-limit fields. The existing widgets can consume a correctly sourced Host report. [Helper recorder][usage-recorder] · [Existing Usage collector][usage-adr] · [Published widget readings][widget-catalog] · [Rex status fields][upstream-protocol]
